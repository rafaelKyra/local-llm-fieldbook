Date: 2026-10-10
Model(s) and build: one local 35B mixture-of-experts coder model (a quantised build), loaded in LM Studio with a 100k context; the orchestration arm named "Harness Lab (primary arm)".
Setup (runtime, quant, context, settings): the arm run from its own desktop window by hand, not through the scripted harness. Four sessions of 20 to 55 minutes each, one model. No repeats, no scorer, no controlled task set.
The work: four ordinary jobs on a small mobile-app project and on a web-to-PDF task: fix a list of known defects from an audit summary; a read-only audit that must not change files; make a reader's pages into a searchable PDF; fix a navigation fault in a setup wizard. The project is not named here and none of its data is published.

What happened:
- The scripted runs of this arm call the orchestration directly. They never exercise the state the window shows. Four faults were found only by using the window:
  1. **No Stop control during the first run of a new session.** The backend log showed the session as running the whole time; the window held a stale "idle" copy of it, because the session was returned to the window after the run had already started. Stop appeared only between model calls. Reproduced with a test that returned the wrong status; fixed.
  2. **An internal refusal code was quoted to the user.** A report-correction turn was refused a tool call; the model then wrote the refusal code and a note about it into the visible report. The refusal text and the correction prompt now say the restriction is internal and must not be mentioned. Test fails on the old text.
  3. **A finished task's report was thrown away.** The evidence check stopped its retries and the user got only "Final report blocked", for a task whose output had been verified earlier (a 148-page searchable PDF). The last refused draft is now shown, labelled UNVERIFIED, with the reason. Whether the draft was actually wrong is not decided by this; it is shown so the user can judge.
  4. **An approved plan was executed as one long turn, not step by step.** The request was classified plan-only; after the user said to continue, the continuation ran all eight steps in a single 10-minute turn, with the context compacted in the middle. By design, but the plan's per-step checks did not apply. **Not fixed** (a design change with regression risk); listed as open.
- On the same sessions the model, given a precise prompt, reproduced a fault, fixed it and added a unit test, but the test "failing on old code" was a compile error, not a failing assertion, and the function it tested was not the one the screen called. The arm does not enforce "the red must be an assertion"; this is a gap in what the arm can require, not a model finding.

What I did not check: a statistic. Four sessions on one model say that these faults exist and where they are, not how often they occur or whether another model meets them. The fixes are tested against the arm's own suite (no new failure against a baseline of 46 known failures, compared by identity; 132 golden tests pass), not by a live batch. Whether the fixes change any pass rate is not measured.
