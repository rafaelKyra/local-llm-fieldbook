Changed `parse_date()` in `feed.py` to try a list of accepted formats (`%Y-%m-%d` then the vendor's new day-first `%d/%m/%Y`) and raise `ValueError` with the offending text if none match; `parse_row()` needed no change since it delegates to `parse_date()`. The existing suite (3 tests) still passes, but note it passed before my change too, so it does not prove the new format works — I verified that separately by running `feed.py` directly: `parse_row("04/03/2026,10.5")` -> `(date(2026,3,4), 10.5)`, `parse_row("2026-03-04,10.5")` unchanged, `parse_date(" 25/12/2026 ")` -> `2026-12-25`, and `parse_row("banana,1")` still raises `ValueError`. I could not add regression tests for the new format: `test_feed.py` is protected and cannot be edited, so no test covers `04/03/2026`. Risk: the new format is only known from the vendor's email, so if it actually ships as month-first (`%m/%d/%Y`) the day-first parse would silently produce wrong dates for days <= 12; worth confirming against a real sample file when it arrives.
